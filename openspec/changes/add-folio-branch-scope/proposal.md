## Why

`Folio` (`prisma/schema.prisma`) tiene un único `current_number` compartido por todas las sucursales para cada código de folio. `allocateFolio` (`src/shared/infrastructure/folios/allocateFolio.ts`) incrementa ese contador único en cada `POST /sales`, `/quotes` y `/purchases` (compras resuelve el folio `CP` automáticamente vía `resolveCanonicalFolio`). El resultado verificado en producción: `CP-000001`..`CP-000009` fueron consecutivos de ZARIOZ, pero `CP-000010`..`CP-000012` — el "consecutivo siguiente" según el contador global — en realidad correspondieron a PRADERA, intercalando la numeración fiscal de dos tiendas distintas en una sola secuencia. Esto rompe la expectativa de negocio de que cada sucursal lleve su propio folio consecutivo (requisito típico de control administrativo/fiscal por punto de venta) y hace inauditable la secuencia de cualquier tienda individual.

Folios como RB (abonos), AB, DEV (devoluciones), PP (pago a proveedor) y TS (traspasos) no fueron reportados como afectados y el negocio no los usa como comprobante fiscal por sucursal del mismo modo que TK/TC/COT/CP — se mantienen con contador global.

## What Changes

- Nueva tabla `folio_branch_counters` (`folioId`, `branchId`, `currentNumber`) — un contador independiente por combinación folio×sucursal, con fila creada on-demand en el primer documento de esa sucursal (arranque desde cero, sin backfill).
- Nuevo helper `allocateBranchFolio(tx, folioId, branchId)` (junto al `allocateFolio` existente, que se conserva intacto para RB/AB/DEV/PP/TS) — incrementa atómicamente el contador de esa sucursal y devuelve un `folioCode` con el formato `<prefix><BRANCH_CODE>-<NNNNNN>` (ej. `TK-ZARIOZ-000001`), distinto del legacy `<prefix><NNNNNN>` (ej. `TK-000001`), que se preserva sin migrar.
- `PrismaSaleRepository.createCompleted`/`createCompletedFromQuote`, `PrismaQuoteRepository.createWithItems` y `PrismaPurchaseRepository.createCompleted` pasan a usar `allocateBranchFolio` con el `branchId` de la operación (ya disponible en todos ellos). El resto de repositorios que llaman `allocateFolio` (pagos, traspasos, waybills) no se tocan.
- `sales`, `quotes`, `purchases`: el `@@unique([folioId, folioNumber])` se reemplaza por `@@unique([folioCode])` (columna ya existente, ampliada de `VarChar(40)` a `VarChar(64)` para el formato nuevo, más largo). `inventory_movements.folioCode` se amplía igual (copia el código de venta/compra).
- `GET /api/v1/admin/folios` acepta `?branchId=` opcional (con branch scoping estándar) y expone `branchCurrentNumber`/`nextFolioCode` calculados para esa sucursal — usado por los previews de "siguiente folio" en POS/Cotizaciones (hoy calculan el número client-side a partir del contador global, que dejaría de ser el correcto para TK/TC/COT).
- `GET /api/v1/admin/folios/:id/audit` acepta `?branchId=` opcional: con él, audita la serie por sucursal (filtrando `folio_code` con el patrón nuevo); sin él, mantiene el comportamiento actual (histórico legacy/contador global).

### Modified Capabilities
- `admin-folios`: nuevo requirement de contadores por sucursal para TK/TC/COT/CP; `GET /folios` y `GET /folios/:id/audit` ganan `?branchId=` opcional.
- `pos-api`: el paso de asignación de folio en "Create sale (atomic emission)" pasa de `allocateFolio` global a `allocateBranchFolio` por sucursal; formato de `folioCode` cambia para folios nuevos.
- `quotes-api`: mismo cambio en "Create quote".
- `purchases-api`: mismo cambio en la resolución automática del folio `CP`.

## Impact

- **Archivos nuevos**: `src/shared/infrastructure/folios/allocateBranchFolio.ts`, `src/shared/domain/folios/formatBranchFolioCode.ts`, migración Prisma.
- **Archivos modificados**: `prisma/schema.prisma` (modelo `FolioBranchCounter`, columnas `folioCode` ampliadas, unique constraints), `PrismaSaleRepository.ts`, `PrismaQuoteRepository.ts`, `PrismaPurchaseRepository.ts`, `FolioRepository`/`FolioDto`/`ListFoliosUseCase`/`AuditFolioSequenceUseCase`/`FoliosController` (módulo `folios`), `app/_hooks/useFoliosOptions.ts`, previews de folio en `CartPanel.tsx`/`QuoteEmitPanel.tsx`/`ConvertQuoteModal.tsx`, `FolioAuditModal.tsx`.
- **Migración de datos**: sólo DDL (nueva tabla, ampliar columnas, reemplazar un unique constraint) — sin backfill de datos existentes. Se aplica primero en dev (`qzzjpyepggwautckqeex`); prod requiere confirmación explícita separada antes de `migrate deploy`.
- **Sin cambios de permisos** — el branch scoping de `?branchId=` en folios reutiliza `resolveScopedBranchId`/`enforceBranchScope` ya existentes.
- **Alcance de pruebas**: unit tests de dominio (`formatBranchFolioCode`), unit tests de use cases con InMemory repos (contadores independientes por sucursal, formato de código), unit tests de controller (branch scoping en list/audit), unit tests de UI (`useFoliosOptions`, previews). Verificación manual en dev con Playwright antes de mergear.
