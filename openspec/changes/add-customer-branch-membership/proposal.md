## Historia de Usuario

| # | Rol | Tarea | Motivo | Criterios de Aceptación | Criterios de Seguridad |
|---|---|---|---|---|---|
| 1 | Operador de sucursal (sin `branches:access_all`) | Como operador de sucursal, quiero ver y crear sólo los clientes asignados a mi propia sucursal en el catálogo, para no confundir clientes de otras tiendas con los míos | Reportado en campo: "clientes mezclados, en la sucursal de ZARIOZ se ven los clientes de las demás sucursales" — genera confusión operativa y riesgo de vender/cotizar al cliente equivocado | - Given un operador de ZARIOZ abre `/catalogs/customers`, When la página carga, Then sólo ve clientes con membresía en ZARIOZ (no ve clientes exclusivos de otra sucursal)<br>- Given el mismo operador crea un cliente nuevo sin especificar sucursal, When lo guarda, Then el backend lo asigna automáticamente a ZARIOZ (su propia sucursal), sin que pueda elegir otra<br>- Given un cliente existe en DB pero NO tiene membresía en ZARIOZ, When el operador intenta abrirlo por id (URL directa) o editarlo, Then recibe 403 (no puede ver ni editar el detalle de un cliente ajeno) | - Filtrado y creación se resuelven server-side (mismo patrón de branch scoping que `products`/`inventory`) — el frontend no filtra client-side una lista sin scope<br>- El operador no puede enviar `branchIds` en el body de creación intentando asignarse a otra sucursal — el backend fuerza su propia sucursal, ignorando cualquier valor distinto |
| 2 | Administrador (`branches:access_all`) | Como administrador, quiero ver todos los clientes y poder asignar explícitamente un cliente a una o varias sucursales, para gestionar clientes que compran en más de una tienda sin duplicar su registro | Hay clientes reales que operan en distintas sucursales de la empresa; el modelo N:M evita crear un registro de cliente por cada tienda donde compra | - Given el admin abre el catálogo de clientes, When la página carga, Then ve TODOS los clientes sin filtrar por sucursal, con un filtro opcional de sucursal disponible<br>- Given el admin crea un cliente nuevo, When completa el formulario, Then debe seleccionar al menos 1 sucursal explícitamente (sin default automático como en el caso del operador) — 400 si `branchIds` viene vacío<br>- Given el admin edita un cliente existente asignado sólo a ZARIOZ, When agrega PRADERA a sus sucursales, Then el cliente queda visible para operadores de ambas sucursales sin duplicar el registro | - Sólo un usuario con `branches:access_all` puede modificar el conjunto de sucursales de un cliente (`branchIds` en `PATCH`) — un operador sin ese permiso que lo envíe recibe el mismo tratamiento que `code` (ignorado/forzado, nunca 500)<br>- El bootstrap de datos existentes (clientes con historial → sus sucursales de venta/cotización/factura; sin historial → sólo Matriz) se ejecuta una sola vez vía migración, sin exponer un job re-ejecutable desde la API |
| 3 | Cajero armando una venta o cotización (cualquier rol) | Como cajero, quiero que el buscador de clientes sólo me muestre (y el backend sólo acepte) clientes asignados a la sucursal de esa operación, para no completar una venta con un cliente que no pertenece a mi tienda | Consecuencia directa de que los clientes ahora tengan sucursal — sin este enforcement en POS/Cotizaciones, el problema reportado seguiría ocurriendo al momento de vender, aunque el catálogo ya esté filtrado | - Given un cajero en ZARIOZ busca cliente en el POS, When escribe un término que matchea un cliente exclusivo de PRADERA, Then ese cliente no aparece en los resultados<br>- Given un admin bypass tenía seleccionado un cliente de PRADERA y cambia la sucursal activa del POS a ZARIOZ antes de confirmar, When confirma la venta, Then el backend rechaza con 400 (defensa en profundidad, no sólo el filtro de UI)<br>- Given un cliente se crea por quick-add directamente desde el POS de ZARIOZ, When se guarda, Then queda asignado automáticamente a ZARIOZ y disponible de inmediato en esa misma venta | - La validación de "cliente pertenece a la sucursal" corre en el use case del backend (`CreateSaleUseCase`/`CreateQuoteUseCase`), no sólo en el buscador del frontend — un `POST` directo con un `customerId` de otra sucursal se rechaza igual<br>- El mensaje de error no revela en qué otra sucursal SÍ está el cliente (mismo principio que el error existente de producto/precio fuera de sucursal) |

## Why

`Customer` (`prisma/schema.prisma`) no tiene ninguna relación con `Branch`. `CustomersController.list` sólo filtra por `search`; `PrismaCustomerRepository.findAll` no aplica ningún `where` de sucursal. El resultado verificado: un operador de ZARIOZ ve el catálogo completo de clientes (16 en dev/QA, cientos en prod potencialmente), incluyendo clientes que sólo compran en otras tiendas — exactamente el reporte de campo "clientes mezclados". A diferencia de `products` (que ya tiene branch scoping vía `branch_inventory`), no existe ninguna tabla puente para clientes.

## What Changes

- Nueva tabla `customer_branches` (N:M `customerId`×`branchId`) — un cliente puede pertenecer a una o varias sucursales.
- Bootstrap de datos existentes (parte de la migración, una sola vez): clientes con ventas, cotizaciones o facturas previas se asignan a las sucursales de esos documentos; el resto se asigna únicamente a la sucursal marcada `is_headquarters` (o, si ninguna lo está, a todas las sucursales activas — evita clientes huérfanos sin ninguna sucursal visible).
- Gating **siempre activo** (no depende de `INVENTORY_SCOPE_MODE`) — es una regla de negocio distinta a la de inventario.
- `CustomersController`/`PrismaCustomerRepository`/`CustomerDto`: `list` acepta `?branchId=` con branch scoping estándar (forzado para no-bypass, opcional para bypass); `create`/`update` aceptan `branchIds: string[]` (forzado a la sucursal propia para no-bypass; obligatorio ≥1 para bypass); `getById`/`update`/`softDelete` verifican membresía antes de operar sobre un cliente ajeno.
- `PosLookups.getCustomer` expone `branchIds`; `CreateSaleUseCase`, `CreateQuoteUseCase` (y `UpdateQuoteUseCase`/`EditCompletedSaleUseCase` si permiten cambiar cliente) rechazan con un nuevo error tipado (→ 400) si el cliente no pertenece a la sucursal de la operación.
- Frontend: sección "Sucursales" en `CustomerEditModal` (checklist para bypass, chip read-only para operador), filtro de sucursal en el catálogo (sólo bypass), `branchId` propagado a los buscadores de cliente de POS/Cotizaciones/Abonos, quick-add asigna la sucursal de la venta en curso.

### Modified Capabilities
- `customers-api`: nuevo requirement de membresía por sucursal (tabla, bootstrap); requirements de List/Get/Create/Update ganan branch scoping y `branchIds`.
- `customers-ui`: sección "Sucursales" en el modal, filtro en la lista, quick-add asigna sucursal.
- `pos-api`: nueva validación "customer belongs to branch" en creación de venta → 400.
- `quotes-api`: misma validación en creación de cotización → 400.

## Impact

- **Archivos nuevos**: migración Prisma (`customer_branches` + bootstrap SQL), `CustomerNotAvailableInBranchError` (dominio `pos` y `quotes`), `CustomerBranchNotFoundError` (dominio `customers`).
- **Archivos modificados**: `prisma/schema.prisma`, módulo `src/modules/customers/` completo (entity, DTO, port, use cases, repositorios Prisma/InMemory, controller, DI), `PosLookups`/`PrismaPosLookupService` (`CustomerLookup.branchIds`), `CreateSaleUseCase`/`CreateQuoteUseCase` (y edición si aplica), `app/(private)/catalogs/customers/**`, `app/(private)/pos/_logic/services/{searchCustomers,createCustomer}.ts` + `CustomerPicker`/`CustomerQuickAddModal`, `app/(private)/payments/_logic/services/searchCustomers.ts`, `app/_lib/offline/catalogCache.ts`.
- **Migración de datos**: DDL + bootstrap (asignación por historial + fallback a Matriz). Se aplica primero en dev; prod requiere confirmación explícita separada antes de `migrate deploy`.
- **Sin cambios de permisos nuevos** — reutiliza `products:read`/`products:write`-equivalentes ya existentes de `customers` (`customers:read`/`customers:write`) y el patrón `branches:access_all` ya usado en el resto del sistema.
- **Alcance de pruebas**: unit tests de use cases (InMemory), unit tests de controller (branch scoping), unit tests de POS/Cotizaciones (rechazo de cliente fuera de sucursal), unit tests de UI (modal, filtro, quick-add). Verificación manual en dev con Playwright antes de mergear.
