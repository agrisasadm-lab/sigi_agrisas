Nota: la feature se dividió en 4 historias independientes (guardia de par lote/caducidad, surfacing del mensaje real, guardia de branchId, orden del schema RFC) porque cada una es un cambio de código aislado, testeable por separado, y ninguna depende de que las otras se implementen para tener valor por sí sola.

## Why

Un operador con sucursal ya asignada intentó registrar la primera compra en producción (`total_purchases = 0` en la BD antes de este intento) capturando Caducidad en una línea sin capturar Lote. El backend rechazó correctamente con `400` según la regla ya documentada en `openspec/specs/inventory-lots/spec.md` (lote/caducidad: par completo o ninguno), pero el formulario de `/purchases/new` nunca comunicó esa regla ni mostró el mensaje real: `createPurchase.ts` descarta cualquier 400 no contemplado en sus 3 casos mapeados y muestra un error genérico. El resultado fue un fallo indiagnosticable desde la UI para el usuario final.

La revisión del mismo formulario expuso dos gaps del mismo patrón — `canSubmit` no valida `branchId` vacío para admins bypass, y el schema Zod del RFC de `newProvider` rechaza RFCs válidos en minúsculas por un orden incorrecto en la cadena `.regex()`/`.toUpperCase()` — que conviene corregir en el mismo cambio porque tocan el mismo formulario y el mismo tipo de defecto (validación de cliente incompleta + mensajes de error no accionables).

## What Changes

- El formulario `/purchases/new` bloquea el envío mientras alguna línea tenga Lote o Caducidad capturado sin su pareja, con aviso visual en la línea afectada (Historia 1).
- El formulario `/purchases/new` bloquea el envío mientras un admin con `branches:access_all` no haya elegido sucursal (Historia 3).
- El servicio `createPurchase.ts` deja de convertir cualquier 400 no reconocido en un error genérico: propaga el mensaje real del servidor como un nuevo error tipado del módulo, y la UI lo renderiza (Historia 2).
- El schema Zod de `newProvider.rfc` en `PurchasesController.ts` normaliza a mayúsculas antes de validar el formato, en vez de después (Historia 4) — corrige la implementación para que cumpla lo que `purchases-api/spec.md` ya documenta ("rfc ... upper-normalizado").
- Ajuste de copy: el placeholder "Opcional" del campo Lote se aclara para reflejar que es opcional en pareja con Caducidad, no de forma incondicional.
